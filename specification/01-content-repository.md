# 01 — Content repository

## Repository layout

An organization (or statistical program) has **one data repository**, created by `statera init <folder>`:

```
<repository>/
├── content/          the content: statera.toml, products/, references/, queries/, recipes/, governance/,
│                     dbt/ and docs/ (generated documentation)
├── publications/     register of published editions (written by the process, never by hand)
├── docs/             studies, technical notes and decisions that are not code (free text)
├── pyproject.toml    the Python environment: Statera as a dependency, at the pinned tag; the production
│                     tools as dependency groups (see "Who installs what")
├── uv.lock           the exact versions (Statera included); .python-version, the Python version
├── .gitattributes    LF line endings on every checkout (`* text=auto eol=lf`), binary files
├── .vscode/          recommended extensions, YAML schemas, and tasks for the day-to-day commands
└── .github/          CODEOWNERS (generated) and CI workflows
```

`statera` commands run from **any folder** of the repository: the framework finds `statera.toml` (or
`content/statera.toml`) from the current folder upward. A globally installed `statera` hands each command
off to the version the repository pins (`uv run --project <repository> statera …`), so every computer and
CI run the same rules. `statera doctor` checks the computer and the repository; `statera check` runs what
CI runs (validation, lint and tests).

The repository's CI validates and tests the content on every pull request: the
`.github/workflows/ci.yml` generated by `statera init` (`uv run --locked --all-groups statera check --all`),
or the framework's reusable workflow, `.github/workflows/validate-repository.yml`.

### Who installs what

Most people who open a data repository only **read** the data. The repository's dependencies are therefore
only what reading needs (`statera`: catalog, queries, metrics, recipes, validation); the production tools
are **dependency groups**, with `default-groups = []` so that `uv sync` leaves them out:

| Group | Extra | For |
|---|---|---|
| `produce` | `statera[produce]` | the data team: dbt (the process) and Copier (`new-product`) |
| `legacy-r` | `statera[legacy-r]` | products with `.R` models (reads and writes `.rds`; R itself is installed apart) |
| `legacy-spss` | `statera[legacy-spss]` | products with `.sps` models (reads and writes `.sav`; GNU PSPP is installed apart) |
| `dev` | — | pytest and ruff, for `statera check` |

The legacy groups are declared only by repositories whose products use that language; `statera doctor`
says when one is missing. The global `statera` hands the commands that produce or check (check, run, sync,
docs…) off with `--all-groups`, so the data team gets every group the first time it needs it; the commands
that only read (doctor, query, metric, recipes, status, cuts, evaluate) run with the dependencies alone.
A shared engine other than DuckDB needs its Ibis backend: `statera[postgres]`, `statera[trino]` or
`statera[athena]`; any other source is a connector of the repository or of a package (07).

On Windows, product folders can exceed the 260-character path limit: `statera init` sets
`git config core.longpaths true` and `statera doctor` reports when long paths are disabled.

## `statera.toml`

At the root of `content/`. It identifies the organization and tells the framework where things are. Paths
are relative to the folder of `statera.toml`.

```toml
[project]
name = "labor-stats"
organization = "Labor statistics"   # avoid department names: they change
acronym = "labor-stats"
namespace = "org.example.labor-stats"   # 02-namespace.md
specification = "0.1"
required_version = "~=0.4.0"         # Statera versions accepted (PEP 440); commands refuse others
repository_root = ".."               # repository root, where .github/CODEOWNERS lives (default: the git root)
synthetic = false                    # true marks all output as SYNTHETIC DATA

[engine]
type = "duckdb"                      # or postgres, trino...
path = "dbt/data/warehouse.duckdb"

[consumption]                        # optional: where those who only read the data read it from (07)
engine = "s3://labor-stats/warehouse.duckdb"   # a DuckDB file (path, https://, s3://) or an engine URL

[conventions]                        # names of the convention columns in the organization's data (English defaults)
period_column = "reference_month"    # reference period (default: period)
cut_date_column = "snapshot_date"    # cut-off date (default: cut_date)
valid_from_column = "effective_from" # start of the reference tables' validity period (default: valid_from)
valid_to_column = "effective_to"     # end of the validity period (default: valid_to)

[dbt]
folder = "dbt"                       # macros/, generated/, dbt_packages/; dbt_project.yml lives in content/
project = "statera_labor_stats"      # dbt project name (default: the name, with _)
profile = "statera_labor_stats"      # (default: same)

[registry]
editions = "../publications"         # edition-by-edition register (default: ../publications)

[openlineage]
namespace = "org.example.labor-stats"

[demo]                               # optional, only for `statera demo`
editions = [                         # in order; each edition first releases the missing cuts (09)
  { product = "employment-flows", period = "2026-05" },
  { product = "monthly-earnings", period = "2026-03" },
]
```

The synthetic data of the demo comes from the products' `SyntheticSource` classes
(`<product>/3-build/synthetic.py`, run by `statera synthetic`, 05). The `[demo] synthetic =
"file.py:function"` hook of 0.5 is still accepted in 0.6 when no product has such a class.

Column names belong to the content and may follow the organization's own language and conventions; the
`[conventions]` section tells the framework which columns play the role of reference period, cut-off date and validity period (09).

The CLI only assumes a default product when the repository has a single dissemination product; with
more than one, `--product` is required (`run`, `resume`, `status`, `evaluate`).

**Names.** The repository name and the namespace **must not** carry the name of a department or
business unit: the organizational structure changes with every reorganization, and the statistical
products remain. A single repository holds the content (`content/`), the editions register
(`publications/`) and the studies and documentation that are not code (`docs/`, such as the
assessment of the current situation).

## Units

A **unit** is a product or a reference table. Its name is unique within the organization (lowercase and
hyphens) and forms part of the identifier (02). A product declares, in `product.odps.yaml`, its
**alignment** (`alignment`) and **visibility** (`visibility`) (09): dissemination, or internal
(source-aligned or aggregate), read by other products in released cuts.

| Type | Folder | Recognized by | Typical phases |
|---|---|---|---|
| Dissemination product (`alignment: consumer`) | `products/<name>/` | `1-specify/product.odps.yaml` | 1 to 8 (its recurring queries live in `queries/`, with `product` naming it, 07) |
| Source-aligned internal product (`alignment: source`) | `products/<name>/` | same | 1, 2, 3, 4 (bronze in batches), 5 (staging), 7 (cuts) |
| Aggregate internal product (`alignment: aggregate`) | `products/<name>/` | same | 1, 2, 5 (silver per cut, rules), 6, 7 (cuts) |
| Reference table | `references/<name>/` | a `*.odcs.yaml` in the folder | — (CSV + contract with temporality, 09) |

The `domain` unit type of the first versions was replaced by the aggregate internal product
(09): what several products share now has an owner, an output contract, authorized consumers and
cuts.

Inside products, folders follow the GSBPM 5.1 phases: `1-specify`, `2-design`, `3-build`,
`4-collect`, `5-process`, `6-analyse`, `7-disseminate`, `8-evaluate`. A unit only has the phases
that apply to it.

## What goes in each phase

| Phase | File | Schema |
|---|---|---|
| 1 | `product.odps.yaml`; `classification.yaml`; `owners.yaml`; `calendar.yaml` (dissemination products) | ODPS 1.0 (profile 04); `classification`, `owners`, `calendar` |
| 2 | `process.yaml`, the product's single process, and next to it what is generated from it: `process.bpmn`, the diagram `process.svg` and the viewer `process.html`; the `processes/` folder of 0.5 fails validation | `process` (05) |
| 3 | tests; `synthetic.py` with the `SyntheticSource` classes (from 0.6, 05) | — |
| 4 | `contracts/*.odcs.yaml` (bronze) | ODCS 3.1 (profile 04) |
| 5 | `contracts/*.odcs.yaml`, `models/` (dbt: `.sql`, or `.py` with pandas; legacy `.sps` or `.R` called by a `.py`), `rules/<RN>/{rule.md,cases.yaml}`, `macros/`, `metrics.yaml` | ODCS; `rule-cases`; `metrics` |
| 6 | `controls.yaml`, `dbt-tests/*.sql`; from 0.6, `checks.py` with the product's `Check` classes and `check-cases/<Check>.yaml` (05) | `controls` (06); check cases (05) |
| 7 | `series.yaml`, `summary.md.j2` (dissemination); `data/<date>/cut.json`, generated (internal) | `publication-series` (06); cut manifest (09) |
| 8 | `indicators.yaml` | `indicators` (06) |

In any phase, `tasks.py` holds the product's own `Task` and `Await` classes, the steps its process names that
the framework does not provide (from 0.6, 05).

Cross-cutting: `governance/` (`roles.yaml`, `shared-owners.yaml`, ADRs, `processes/`),
`queries/`, `recipes/` (07), `dbt/` and `docs/` (generated documentation), all in `content/`.

There is a single dbt project, and it **must** have `dbt_project.yml`, `packages.yml` (generated by
`statera sync` with the path of the installed package, outside git) and `profiles.yml` at the root
of `content/` (next to `statera.toml`), so that the units' models, seeds and tests are inside the
project. `dbt/` holds only `macros/`, `generated/` and `dbt_packages/`.

## Python models and legacy code (SPSS and R)

A dbt model **may** be written in Python (dbt Python model, with pandas) when the transformation is
clearer that way. The `<model>.py` file sits in the same folder as the SQL models and **must**
isolate the rule in a pure function, `transform(inputs, variables) -> DataFrame`, called by
`model(dbt, session)`. This way, the Python model gets the same treatment as SQL: contract, tests,
group and access, lineage and execution by the process (`dbt:build`). Differences:

- names in `dbt.ref()` **must** be literals (dbt reads them from the code to build the lineage), and
  dbt variables arrive through the model's `config` in the `.yml` (`cut_date: "{{ var('cut_date') }}"`);
- dbt only runs *unit tests* for SQL: the rule cases of a Python model are run by the framework,
  calling `transform` (`statera rules test`, and the `rules` validation group);
- the rule is cited in the model's `meta`: `dbt.config(meta={"rules": [...]})`.

**Legacy SPSS syntax** runs without rewriting through **GNU PSPP**, called from a Python model
(`statera.legacy.pspp.run`). The only adaptation of the `.sps` is replacing file paths with
FILE HANDLEs (`GET FILE=records.` … `SAVE OUTFILE=result.`), which the framework defines with
the inputs written as `.sav`. The rule cases declare `requires: [pspp]`: without PSPP, they are left
not run (`not-run`); CI installs it and **requires** them (`STATERA_REQUIRE=pspp,r`). PSPP is not SPSS:
before its result replaces SPSS's, equivalence **must** be certified by a script that compares both
outputs on the same inputs.

**Legacy R scripts** run the same way, through `Rscript --vanilla`, called from a Python model
(`statera.legacy.r.run`). Inputs go as `.rds` and the framework defines, at the start of the script,
`inputs$<name>` (path of each input) and `output` (where to write the result): the adaptation is
replacing paths with `readRDS(inputs$records)` and `saveRDS(result, output)`. The framework
does not require R packages; those the script uses must be installed in the environment. The cases
declare `requires: [r]`.

## Product skeleton

Every product **must** have the same files, so that whoever opens any product knows where to look
for each thing. A file that does not apply **is not missing**: it declares `not_applicable: <reason>`,
which distinguishes "does not apply" from "was forgotten". Conformance (08) treats a `not_applicable`
as absence of content at the levels that require it, and shows the reason.

| File | Dissemination | Internal (source-aligned or aggregate) |
|---|---|---|
| `1-specify/calendar.yaml` | cut-off and release dates of each edition | **generated**: the cuts requested by the consumers' calendars, including through other internal products |
| `2-design/process.yaml` | the product's process (execution plan) | same |
| `6-analyse/controls.yaml` | controls across editions | controls of the load or of the cut, or `not_applicable` (quality in the contracts) |
| `7-disseminate/series.yaml` | publication series | **always** `not_applicable`: an internal product is not disseminated |
| `8-evaluate/indicators.yaml` | quality indicators and action plan | service indicators (delay, completeness) |

The product template (`statera new-product <name> --alignment consumer|aggregate|source`) creates the
skeleton with `not_applicable: "to be defined: …"` where there is no content yet, and the
product starts with `conformanceLevel: 0` (draft, 08): validation accepts the skeleton, and
`statera conformance` shows what is missing. Validation (group `skeleton`) fails when a file is
missing, when the reason is empty, when an internal product has a series and when the calendar of an
internal product is not the generated one.

## Data

Each phase of each unit **must** keep what runs produce in `data/`, outside version control. With the
`STATERA_DATA` variable, all `data/` folders move to
`$STATERA_DATA/<products|references>/<unit>/<phase>/` (tests, ephemeral environments). The engine
stays where `statera.toml` says.

## Generated files

They are not edited by hand; CI **must** fail if they are out of date:
`dbt_project.yml`, `dbt/generated/*.yml`, the `calendar.yaml` of internal products,
`**/2-design/*.bpmn`, `.github/CODEOWNERS` (at the repository root,
`[project] repository_root`). The diagram and viewer next to each process (`2-design/process.svg` and
`.html`) and the documentation in `content/docs/` are also generated, but not checked by CI;
`statera sync` regenerates them all except the documentation (`statera docs`).

Each generated file **must** start with the framework notice (`statera.generated`), as a comment in the
format's syntax. The notice says that the file is generated, by which command, from which sources
and how to change it. The content repository **must** mark the same files as
`linguist-generated=true` in `.gitattributes`, and **may** open them read-only in the editor
(`files.readonlyInclude` in VS Code). The `.bpmn` files are left out of that list, because people
draw in them and then import the change into the YAML.
